对象存储管理服务
PostgreSQL + MinIO + FastAPI

设计 面向千万级对象目录：统一接入、对象查找、容量统计、可控删除，以及可恢复的数据一致性。本文定义第一版可实施范围，并明确哪些指标需要在真实负载下验证。

版本 v1部署形态：Linux / 容器文件存储：MinIO索引与业务状态：PostgreSQL服务：FastAPI
核心决策

设计 MinIO 是文件字节的权威来源；PostgreSQL 是业务对象目录和查询入口。客户端通过短时签名表单直传，FastAPI 核验上传结果后将对象置为可见。删除由后台任务重试，统计由数据库事件异步汇总。

查找

设计 支持租户内按名称、桶、时间、大小、类型和预定义标签筛选；分页使用游标。

统计

设计 提供对象数、逻辑字节、按桶与日期聚合；展示汇总时间与统计延迟。

扩展

设计 API 与 Worker 无状态水平扩容。PG 先单主高可用，待压测证明必要时再分区或拆分查询负载。

01 · 目标与边界

v1 包含

  • 设计 多租户访问控制；服务端生成不可变对象 key。
  • 设计 单次直传，上限暂定 1 GiB；上传发起、完成核验、查询、下载、删除。
  • 设计 对象元数据与业务标签查询；桶级及日级逻辑用量统计。
  • 设计 失败重试、过期上传清理、抽样核对与全量周期核对。

v1 不包含

  • 设计 文件正文检索、OCR、图像相似检索。
  • 设计 跨地域双活、自动分库分片和用户自助创建 MinIO 桶。
  • 设计 大于 1 GiB 文件的 multipart 编排；作为后续迭代。
  • 待确认 法规留存、不可删除对象、跨租户共享等业务规则。
边界 “统计用量”默认指业务对象逻辑字节与记录数，不等于纠删码、版本、未完成上传或副本带来的物理占用；物理容量由 MinIO 指标单独监控。

02 · 总体架构

客户端 / 管理台认证 · 查找 · 直传
→
FastAPI 服务授权 · 目录 · 签名 · 核验
↔
PostgreSQL对象记录 · 任务 · 汇总
MinIO 集群客户端经短时 POST 签名表单直传；API/Worker 使用服务账号核验与删除
Worker + Scheduler删除重试 · 统计汇总 · 过期清理 · 对账
监控API / PG / MinIO / Worker 指标、日志、告警

依据 MinIO Python SDK 提供 presigned_post_policy、stat_object、presigned_get_object 与 remove_object 等能力；FastAPI 官方文档支持按路由与依赖拆分服务，见 Bigger Applications。实际采用版本需在锁定依赖时验证。

部署前提 v1 所有对象写入和删除必须走本服务。若其他客户端拥有同桶写权限，事件订阅与全量对账须提升为正式的同步路径；否则 PG 目录无法保证完整。

03 · 数据模型

设计 使用独立的对象 ID 对外展示；MinIO key 由服务生成，例如 tenant UUID / object UUID。原始文件名只保存在 PG，避免重名覆盖和用户输入进入物理 key。

表关键字段职责与约束
objectsid, tenant_id, bucket, object_key, display_name, size_bytes, content_type, metadata_json, status, created_at, ready_at, deleted_at设计 一行对应一个物理对象。唯一约束：bucket + object_key。`status` 为 pending / ready / deleting / deleted / failed；查询默认只见 ready。
upload_sessionsid, object_id, tenant_id, idempotency_key, expected_size, expires_at, completed_at设计 保存上传授权与幂等键；同租户同幂等键返回同一会话。过期会话进入清理流程。
jobsid, kind, object_id, attempts, next_run_at, locked_at, done_at, last_error设计 与状态变更在同一 PG 事务内写入；Worker 领取删除、清理、对账任务并重试。
stats_eventsid, object_id, event_kind, bucket, day, size_delta, processed_at设计 ready 与 deleted 转移各写一个唯一事件，防止重复计数。
stats_dailytenant_id, bucket, day, object_count, size_bytes, updated_at设计 查询用汇总表；聚合 Worker 在事务中应用增量并标记事件已处理。

首批索引

用途索引建议说明
对象定位UNIQUE(bucket, object_key)；PRIMARY KEY(id)设计 物理 key 不复用；API 每次按 tenant_id 再授权。
默认列表(tenant_id, status, ready_at DESC, id DESC)设计 对应默认排序与游标，避免深 OFFSET。
桶内列表(tenant_id, bucket, status, ready_at DESC, id DESC)设计 若桶内列表占主要流量则保留，否则以压测结果裁剪。
灵活标签metadata_json 的 GIN 索引，按需启用设计 仅在确有该类查询时增加；高频字段可提升为独立列。

依据 PostgreSQL 多列索引、JSONB GIN 索引和分区建议。千万级对象不作为自动分区的充分条件。

04 · 核心流程

上传：先占位，后核验，再可见

  1. 设计 客户端调用发起接口，提交文件名、大小、类型、标签和幂等键；服务校验租户额度与字段，并在 PG 建立 pending 对象与 upload_session。
  2. 设计 服务生成仅可写指定 bucket/key、有限时间及大小范围的 POST 签名表单；建议签名有效期 10 分钟，会话有效期 30 分钟。
  3. 设计 客户端直传 MinIO，再调用完成接口；服务通过 stat_object 核验对象存在与实际大小，检查会话未过期。
  4. 设计 PG 事务将状态由 pending 改为 ready，同时插入统计事件；重复完成请求返回已完成结果。
  5. 设计 过期会话由 Worker 清理 MinIO 残留并标为 failed。若业务要求强内容校验，另增 SHA-256 校验路径，不把 ETag 当作通用内容哈希。

下载与删除

下载

设计 API 校验租户、对象状态和下载权限，返回短时 GET 签名 URL（建议 5 分钟）。审计记录签发行为；若需逐字节审计或内容检查，改为代理下载。

删除

设计 API 在 PG 事务中将 ready 置为 deleting，并写入 jobs，返回 202。Worker 删除 MinIO 对象后，再在 PG 将状态置为 deleted 且写统计负增量；失败按退避策略重试。

边界 MinIO 操作和 PG 事务不能组成一个原子事务。服务必须容忍“对象已上传、目录未发布”和“目录标记删除、物理对象尚未删”两个中间态，并由任务与对账修复。

05 · API 契约草案

设计 前缀统一为 /api/v1；请求身份来自 JWT，tenant_id 从可信令牌或服务端映射获取，不接受用户自行指定租户。所有写接口使用 Idempotency-Key。

方法与路径输入 / 输出核心字段状态与错误
POST /uploads文件名、期望大小、类型、标签；返回 upload_id、object_id、POST URL、表单字段、expires_at201；400 字段错误；409 幂等冲突；413 超限；429 限流
POST /uploads/{id}/complete返回对象 ID、实际大小、ready_at200；404 会话不存在；409 状态冲突；422 核验不匹配；503 MinIO 暂不可用
GET /objectsbucket、name_prefix、类型、时间/大小区间、标签、limit、cursor；返回 items、next_cursor200；400 无效筛选；403 无权限
GET /objects/{id}返回对象元数据，不返回 MinIO 凭据200；404 不存在或无权限
POST /objects/{id}/download-url返回短时 URL 与到期时间200；404；409 非 ready；429
DELETE /objects/{id}返回任务 ID 与 deleting 状态202；404；已删除时幂等返回 204
GET /stats/overview对象数、逻辑字节、as_of、lag_seconds200；统计滞后时仍返回可见时间
GET /stats/buckets按桶统计，可指定日期区间200；限制最大时间跨度

设计 `GET /objects` 每页最多 100 条；游标编码排序键与过滤条件摘要，过滤条件变化则返回 400。错误响应统一包含 code、message、request_id。

06 · 查找与统计策略

查询路径

  • 设计 精确对象 ID 查询走主键。
  • 设计 列表查询固定 tenant_id、status=ready；常用筛选建组合索引。
  • 设计 文件名先支持前缀，不承诺任意子串高性能；标签查询先限定可搜索字段。
  • 设计 结果按 ready_at、id 稳定排序并用游标翻页。

统计路径

  • 设计 对象 ready/deleted 产生统计事件，Worker 批量归并。
  • 设计 查询直接读取 stats_daily 汇总，标示 as_of。
  • 设计 每日比较汇总与 PG 对象明细；发现差异自动重建受影响桶/日。
  • 设计 物理容量与业务逻辑容量分别展示。

依据 PostgreSQL 的全表精确计数需要检查记录可见性，不宜把频繁看板建立在每次扫描全部对象之上；见 Slow Counting。大 OFFSET 仍需计算跳过的行；见 LIMIT/OFFSET。

07 · 一致性、幂等与修复

故障点可见状态恢复动作
发起上传后客户端未传pending，不对外显示设计 会话超时后标 failed；不计入统计。
文件已上传但 complete 未到达pending，MinIO 有孤儿对象设计 客户端可重试 complete；超时清理任务先 HEAD 再删除。
complete 重试或并发ready 只转移一次设计 使用状态条件更新与唯一统计事件；返回同一 object_id。
删除 MinIO 失败deleting，不可下载设计 jobs 保留并指数退避重试；超过阈值告警。
删除成功、更新 PG 失败deleting设计 重试删除按幂等处理，随后提交状态与统计事件。
统计 Worker 崩溃对象状态准确，统计可能滞后设计 统计事件与汇总更新在同一事务提交；未处理事件重领。

对账分层

每 5 分钟：过期 pending每 5 分钟：失败任务重试每日：统计明细对账每周：按 key 范围全量对象核对

设计 全量核对采用分页扫描并限速；记录游标，允许中断续跑。对 PG ready 但 MinIO 缺失的记录只标记异常并报警，不自动删除业务记录；对 MinIO 孤儿对象先隔离与记录，再按保留规则清理。

08 · 安全设计

  • 设计 FastAPI 校验 JWT 签名、issuer、audience、过期时间及访问范围；每个对象读写都绑定 tenant_id，管理员跨租户查询单独授权。FastAPI scopes 文档
  • 设计 MinIO 桶默认私有；客户端只拿单对象、短时有效的上传表单或下载 URL，不拿长期 Access Key。
  • 设计 服务器凭据使用 Secret 管理，按读、写、删除职责拆分；PG 账号按迁移、API、Worker 分权。
  • 设计 强制 TLS；限制上传大小、类型、元数据键和值长度；客户端文件名只作为展示文本，下载响应安全编码。
  • 设计 审计上传发起、完成、下载签发、删除及管理员操作；日志不包含签名 URL、JWT 或凭据。

09 · 部署与运维

组件生产建议故障与备份
FastAPI设计 至少 2 实例，负载均衡；独立健康检查与连接池上限。无状态重启；数据库或 MinIO 异常时返回明确 503。
Worker / Scheduler设计 Worker 可多副本；任务领取使用行锁跳过已锁任务；Scheduler 单活租约。任务保存在 PG，可重试与人工重放。
PostgreSQL设计 单主 + 备库 + PITR；监控连接、WAL、复制延迟、死元组、慢查询。定期恢复演练；迁移使用向前兼容步骤。
MinIO设计 生产采用分布式部署；容量、对象数、失败请求和磁盘状态独立监控。版本策略与备份/复制按 RPO、RTO 另行确定。

一键启停交付

设计 仓库后续交付 compose.yaml、环境变量模板，以及 Linux 下的 start.sh / stop.sh。脚本负责健康检查与迁移前置校验；生产数据库和 MinIO 可指向外部托管集群。本文是设计稿，不包含实际部署脚本。

观测与告警

设计 关键指标：API p95/p99、上传完成失败率、PG 查询与连接池、Worker 待办数/最老任务年龄、统计延迟、PG/MinIO 容量差异、对账异常数量。日志带 request_id、tenant_id、object_id，禁止记录签名 URL。

10 · 容量与性能验证

估算 基线规模按 1,000 万条 ready 对象设计；平均对象大小、元数据长度、租户分布、更新率和 QPS 尚未知，因此不在设计稿承诺数据库磁盘容量或实际响应时间。数据库占用应通过“对象行 + 索引 + WAL + 历史版本 + 预留空间”实测。
验收负载目标值测量方式
按 ID 查对象目标 p95 ≤ 100 ms1,000 万条样本，含租户鉴权；报告 DB 与 API 分段耗时。
常见过滤列表目标 p95 ≤ 300 ms，每页 100 条覆盖桶、时间范围、名称前缀、标签；观察扫描行数与索引命中。
上传完成接口目标 p95 ≤ 500 ms，不计文件传输包含 MinIO stat 与 PG 提交；注入重试和并发 complete。
统计新鲜度目标 正常情况下 ≤ 5 分钟持续写入下比较 ready 明细与汇总时间。
故障修复目标 失败任务重试无重复计数在上传、完成、删除、统计事务前后注入故障。

目标 上述数字是待验证的验收门槛，不是 PostgreSQL 或 MinIO 的通用性能承诺。压测必须记录机器配置、PG 参数、索引大小、缓存命中率、对象分布和并发模型。

设计 若真实查询触发大范围扫描，先优化索引和查询形态；若统计成为热点，优化批量汇总；若 PG 写入、WAL 或存储持续饱和，再评估分区、读副本或专用搜索引擎。PG 文档提醒分区键和分区数量需根据真实查询选择，见 分区最佳实践。

11 · 交付阶段与验收

阶段 A · 基础能力

设计 数据迁移、身份鉴权、上传三段流程、下载签名、对象列表和详情。验收：重复上传完成不产生重复记录；其他租户无法读取对象。

阶段 B · 稳定性

设计 删除任务、过期清理、统计事件、指标告警。验收：故障注入后最终状态正确且统计不重复。

阶段 C · 规模验证

设计 生成千万级代表性目录、查询压测、对账与恢复演练。验收：达到本方案 SLO 或记录瓶颈及调整结论。
