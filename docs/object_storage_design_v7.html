对象存储与文档版本管理
PostgreSQL + MinIO + FastAPI

设计 保留 v2 的通用对象上传、查找、下载、删除和桶级统计；在同一对象目录之上提供数千万篇文档、版本、正文与图片附件的关系管理。PostgreSQL 管理目录和引用，MinIO 保存字节。

版本 v7对象层：objects文档层：documents / versions / assets自定义标签与检索一致性契约HTML 单文件方案
核心选择：一套正式对象目录，两类入口

设计 `objects` 是所有正式 MinIO 对象的唯一目录，临时上传由 upload_sessions 管理。对象目录独立支持 v2 的通用操作；文档版本只引用已就绪 objects。正文和附件全部就绪后，在 PostgreSQL 事务中发布版本并切换当前版本。被引用对象不能通过通用删除接口直接删除。

对象层 · 延续 v2

设计 上传会话、对象列表、按条件查找、签名下载、异步删除和桶级统计继续可用。

文档层 · 延续 v3

设计 稳定文档 ID、追加式版本、正文对象引用、图片附件关系和当前版本指针。

单一权威

设计 PG 的 objects 记录 MinIO 位置与状态；文档层只引用 object_id，不另建第二套物理对象目录。

01 · 场景与范围

对象层：保留 v2

  • 设计 支持独立文件的上传会话、对象详情、按桶/名称/时间/大小/类型及自定义标签筛选。
  • 设计 支持短时下载 URL、异步删除、失败重试、过期上传清理和对象对账。
  • 设计 保留桶级当前对象数/逻辑字节与每日新增、删除统计。

文档层：保留 v3

  • 依据 用户场景：数千万篇文档与图片、持续入库、按 ID 读取、版本及附件关系。
  • 设计 每篇文档有稳定 ID，版本追加，正文和附件指向对象层记录。
  • 设计 历史版默认保留；OCR、正文全文检索和跨地域双活不在第一版。
口径 对象数、文档数、版本数和附件关系数分别统计。MinIO 物理容量还受冗余、历史对象版本等影响，不能由 PG 逻辑字节直接推得。

文档类型规则

结论 `documents.doc_type` 表示逻辑文档的业务类型；`objects.content_type` 表示文件字节的 MIME 类型。两者独立：一篇 paper 可关联 PDF、图片和 JSON 对象；一个 image_record 也可有元数据版本和衍生附件。
层次字段与示例规则
统一分类documents.doc_type = article / paper / report / image_record设计 必填、受 document_types 外键约束；API 返回 code 与展示名。类型 code 不复用、不因展示名改变而变更。
通用元数据source、external_id、title、created_at 等设计 跨类型都要查询的字段保留为普通列；`documents.attrs_jsonb` 只放随逻辑文档稳定的补充属性。
类型专有属性paper: doi / journal；article: channel；image_record: width / height设计 随内容版本变化的属性放 `document_versions.attrs_jsonb` 并保留快照与规则版本。FastAPI 按 doc_type 选择已部署的校验模型；高频筛选字段在明确查询需求后提升为列或表达式索引。
附件角色raw / body / cover / inline_image / attachment设计 原文与正文由版本对象字段引用，其他角色由 document_assets.role 标识；发布时按类型检查必需对象与允许角色。

设计 创建文档时确定 doc_type；普通版本发布不得悄悄更改它。若来源分类纠错，走受权的重分类操作：用新类型校验属性和附件，追加一个引用原有对象的新版本，在同一事务内更新 documents.doc_type 与 current_version_id，并记录旧值、新值、操作者和时间。旧版本保留原 doc_type_snapshot，不回写历史。来源身份唯一键仍为 `(tenant_id, source, external_id)`，避免同一来源记录因类型变化被拆成两篇文档。

待确认 以上类型 code 仅为示例；正式类型清单、每类必填属性、允许的附件角色和“图片是否作为独立文档”应根据真实数据源确定。PostgreSQL JSONB 文档支持存储和按需索引差异化属性。

自定义标签与检索

设计 同一租户内，对象与文档共用可复选的标签字典，但各自拥有独立的标签关系。录入时可选已有标签，也可提交新名称；服务端在绑定事务中自动创建不存在的标签。
环节行为与边界
选择与新建设计 输入框查询当前租户标签建议；提交既可包含已有 tag_id，也可包含新 tag_name。服务端统一做去首尾空白、Unicode NFC 与大小写归一，再按 `(tenant_id, normalized_name)` 查找或创建。空白及超长名称按配置拒绝。
并发同名设计 标签字典以数据库 UNIQUE 约束为最终防线；并发创建用 `INSERT ... ON CONFLICT DO NOTHING`，随后在同一事务的新语句中读取已有 ID，再插入关系。重复提交同一绑定保持幂等。
绑定范围设计 对象标签落在 object_tags；文档标签落在 document_tags。文档标签随逻辑文档存在，新增版本仍可看到；附件对象不自动继承文档标签。需要按附件对象查找时，应明确给该对象绑定标签。
标签检索设计 `/objects` 只查直接绑定的对象标签，`/documents` 只查文档标签。`tag=名称` 支持单标签精确查找；多标签用 tag_ids 与 `all`（同时具备）或 `any`（具备其一），结合租户、状态和游标分页。搜索未知标签返回空列表，不自动建标签。
权限与保留设计 只能选择本租户的标签；标签变更沿用目标对象/文档的编辑权限。document_internal 对象仍受文档权限约束。解绑后标签字典保留供以后选择；停用标签不再建议新绑定，既有绑定仍可查询。
一致性与删除设计 新标签创建与对象/文档绑定在一个 PG 事务中提交；关系表的复合外键防止跨租户和悬空绑定。对象转为 deleted 后清理其标签关系；文档最终清理时同理，标签字典仍保留。

设计 为避免标签搜索扩散成全文搜索，首版按规范化名称精确匹配筛选，建议列表可做前缀查询。标签与对象、文档的关联属于 PostgreSQL 元数据，不写入 MinIO 对象 metadata；给文档贴标签也不增加对象计数。容量评估需按“实体数 × 平均标签数”估算两张关系表，装载代表性标签分布后测多标签查询。

依据 PostgreSQL 的 ON CONFLICT、唯一约束与外键可支撑并发创建及关系约束；组合索引的适用性需根据实际查询条件验证。

04 · 对象入库与版本发布

独立对象：v2 能力，强化写入保护

设计 `/uploads` 建 pending 对象并签发仅可写 staging key 的短时凭证；客户端直传；`complete` 核验 staging 后由服务端复制到唯一正式 key，再核验正式对象，最后置 ready。过期清理、幂等重试和对象统计继续生效。

文档入库：复用对象层

设计 文档会话为原文、正文和附件分别创建对象层上传会话；采集器完成全部对象后发布文档版本。客户端不持有正式对象前缀的写权限。

文档版本发布

  1. 设计 采集器提交 source、external_id、doc_type、ingest_key；API 校验类型 code，定位或创建 documents，在文档行锁下分配 version_no 并创建 staging 版本。已有文档的 doc_type 不匹配时返回 409，交由重分类流程处理；重复 ingest_key 返回原会话。
  2. 设计 原文、正文与附件均走对象层 staging → 正式 key 的完成流程。正式 key 不复用且仅服务端可写；对象层核验正式对象存在与大小。若要求强 SHA-256 校验，需受控流式校验或可信采集器证明，不将 multipart ETag 视作 SHA-256。
  3. 设计 采集器完成文档会话；FastAPI 按 doc_type 校验版本属性和必需对象，再在 PG 事务中锁定文档和所引用的 objects 行，确认同租户且全部 ready，写入版本属性快照、正文及附件关系，将版本置 ready，并按发布策略更新 current_version_id。
  4. 设计 同一事务写入文档统计事件；对象层对象在上传完成时已各自计入对象统计。文档发布不得再次累加对象数或对象字节。
  5. 设计 已完成的最高 version_no 默认成为当前版本；晚到旧修订保留为历史。若来源 revision 可靠，可按其排序。

依据 MinIO Python SDK 提供服务端 copy_object 与 stat_object。SDK 文档列出单次 copy_object 的源对象大小上限 5 GiB；v2 暂定单文件上限 1 GiB，超限文件需单独设计 multipart/compose 流程。正式复制会增加存储端 I/O 与短时空间占用，需压测。

一致性边界 MinIO 与 PG 不共享事务。已上传但文档未发布的 ready 对象可作为暂存对象保留至文档会话 TTL；只有确认无任何版本引用且过保留期后才进入通用删除任务。

05 · 对象与文档读取

对象入口：延续 v2

设计 `/objects` 保留桶、名称前缀、类型、时间、大小筛选，并增加按自定义标签筛选；按对象 ID 查详情，签发短时下载 URL。列表使用游标分页。

文档入口：延续 v3

设计 按 document ID 查当前版本，按版本号查历史；`/documents` 支持按自定义标签查找。响应以 object_id 描述正文与附件；附件关系固定在版本上，历史版清单不随当前版变化。

设计 普通对象用户可管理其租户内的 standalone 对象；document_internal 对象仅通过授权文档访问。对象管理员可查看完整物理目录。文档列表不批量展开所有附件，详情按需读取。

07 · 索引与容量

表 / 查询首批索引选择理由
objects 物理定位PRIMARY KEY(id)；UNIQUE(bucket, object_key)设计 v2 独立对象和 v4 文档对象共用唯一目录，避免同一物理对象重复登记。
objects 列表(tenant_id, status, ready_at DESC, id DESC)；桶内列表按实测加 bucket 前导列设计 延续 v2 的查找与游标分页；不预建所有筛选组合。
documents 按 IDPRIMARY KEY(id)；必要时 `(tenant_id, id)`设计 按 ID 定位是主路径；权限过滤必须包含租户或访问范围。
来源幂等UNIQUE(tenant_id, source, external_id)设计 同一来源对象只对应一个逻辑文档。
版本读取UNIQUE(document_id, version_no)；UNIQUE(document_id, ingest_key)设计 快速取历史版本，并约束重试。
附件列表(version_id, role, ordinal)设计 先按版本定位，再按角色和顺序展示。
文档类型筛选按实测选择 `(tenant_id, doc_type, created_at DESC, id DESC)`设计 仅在类型 + 时间列表是高频路径时建立；`doc_type` 单列索引是否有益需看选择性与查询计划。
差异化属性按需添加 JSONB GIN 或表达式索引设计 避免把整个 JSONB 默认索引化导致入库成本上升。
标签选择与并发创建tags: UNIQUE(tenant_id, normalized_name)设计 同租户规范化后同名仅保留一个标签；前缀建议的查询计划需单独实测。
对象标签查找object_tags: UNIQUE(tenant_id, object_id, tag_id)；另建 (tenant_id, tag_id, object_id)设计 前者服务对象详情和去重，后者从标签定位对象；再过滤 objects.status、purpose 与权限范围。
文档标签查找document_tags: UNIQUE(tenant_id, document_id, tag_id)；另建 (tenant_id, tag_id, document_id)设计 前者服务文档详情，后者从标签定位文档；多标签 all/any 与时间排序应在代表性数据上 EXPLAIN ANALYZE。

判断 数千万篇文档本身不足以要求分布式数据库。documents 主要按 ID 读，默认不按时间分区；对象层、版本表和附件关系的行数可能明显高于文档数，分别按真实查询与清理方式评估。PostgreSQL 分区文档

估算 若 3,000 万篇文档的有效字段平均为 1 KB，仅 documents 字段载荷约 30 GB（十进制）；对象、版本、附件关系、索引、WAL、备份与预留空间均需另算。用代表性数据装载后实测。

08 · objects 与 documents 的一致性契约

结论 PG 内的“文档—版本—对象”引用可用约束与事务保证；PG 与 MinIO 之间没有跨系统原子事务，只能通过暂存状态、幂等重试、持久任务和对账达到最终一致。对外只发布已经核验并提交的版本。
不变量保证方式
I1 · 引用存在且同租户设计 版本的 raw_object_id、body_object_id 与附件的 object_id 使用复合外键；documents.current_version_id 只可指向自己的版本。
I2 · 已发布版本只引用 ready 对象设计 发布事务先锁 objects 行，再检查同租户、status=ready 和所有必需附件齐全；随后写关系、置版本 ready、切换当前指针，一次提交。
I3 · 已引用对象不得进入 deleting设计 通用删除事务同样先锁 objects 行，检查原文/正文/附件引用及保护会话；有引用返回 409，无引用才改状态并写删除任务。
I4 · 当前版本始终可解析设计 current_version_id 与版本状态在同一事务更新；staging/failed 版本不成为当前版本。版本删除前先处理当前指针。
I5 · 对象计数不重复设计 对象 ready/deleted 转移各产生一次唯一统计事件；文档发布只增加文档/版本统计，不再增加对象统计。

并发协议

  1. 设计 发布事务先锁目标 documents 行，再按 object_id 固定顺序锁所有待引用的 objects 行；复核状态后插入/确认引用并提交。
  2. 设计 删除事务锁定 objects 行，再查询所有版本与附件引用以及未过期的文档入库会话；若任一存在则拒绝，否则置 deleting 并在同一事务写 jobs。
  3. 设计 所有对象状态变更和引用建立只能通过上述服务路径；数据库账号按职责限权。若允许其他程序直接更新这些表，需把状态检查进一步下沉至受控数据库函数或触发器。

依据 PostgreSQL 支持复合外键与行级锁定读取。固定锁顺序是本方案降低死锁风险的设计规则。

故障处理

情形处理
重复采集相同文档设计 `(tenant_id, source, external_id)` 定位逻辑文档；同 ingest_key 返回同一版本，新的有效修订追加版本。
staging 已上传，正式复制失败设计 objects 保持 pending；任务重试复制。上传会话到期后清理 staging，并核对正式位置是否有未登记对象。
正式复制成功，PG ready 提交失败设计 重试先检查正式 key 是否存在且与预期大小/可信校验值相符；相符则完成 PG 状态，不盲目覆盖；不符则隔离并报警。
对象已 ready，文档发布失败设计 版本保持 staging，ready 对象暂受文档会话保护；重试发布或在 TTL 后进行无引用清理。
附件上传不完整设计 整版不发布；详情仍读旧 current_version_id。允许重新上传缺失附件再完成。
两个任务并发发布设计 在文档行上串行更新当前版本指针，并比较版本顺序；唯一约束负责幂等。
通用对象删除与文档引用竞态设计 两条路径都锁定同一 objects 行；删除事务检查无版本/附件引用且无保护会话，才置 deleting 并写 jobs。引用事务只接受 ready 对象。
删除某历史版本设计 先解除正文和附件关系并确认不是当前版本；对象仅在无任何引用且保留期结束后进入通用删除流程。
PG 与 MinIO 不一致设计 定期比对 ready 对象的存在性与暂存对象；缺失对象报警，不静默删除文档关系。

设计 任务重试使用数据库持久化状态；统计与清理事件通过 outbox 事务写入。对账覆盖 staging、正式对象和 PG 目录，并按 key 范围分页、限速、记录游标。正式前缀写删权限仅授予本服务；若外部系统直接修改正式对象，PG 无法即时保证对象仍存在，必须引入事件同步和更频繁对账。

09 · 双层统计与观测

对象层：延续 v2

设计 stats_current 记录各桶当前 ready 对象数与逻辑字节；stats_daily 记录每日上传和删除。文档对象在对象完成时计一次，文档发布不再计入对象总数。

文档层：新增

设计 另统计文档数、已发布版本数、正文引用数、附件关系数。文档层统计可关联对象逻辑字节，但不与桶级容量相加。

设计 两类接口分别返回 as_of；监控对象上传完成率、文档发布失败率、保护期孤儿对象、Worker 积压、按 ID 查询 p95/p99、PG 索引与 WAL 增长及 MinIO 容量。

口径 同一对象可被多个文档版本引用：对象层只计一个物理目录记录，文档层可计多条引用关系。报表必须分别命名。

10 · 部署与恢复

组件生产建议恢复验证
FastAPI / Worker设计 至少双实例、无状态；连接池和并发上限受 PG 容量约束。重启和任务重试不创建重复版本。
PostgreSQL设计 单主与备库、PITR、独立备份；首先优化查询与索引，再考虑读副本。在隔离环境恢复到时间点，校验文档/版本/关系完整。
MinIO设计 分布式部署；生命周期与复制策略按保留要求设定。抽查由 PG objects 定位的独立对象、正文及附件均可读取。
脚本设计 实施阶段交付 compose.yaml、环境模板、Linux start.sh / stop.sh。启动前验证依赖、迁移与凭据，停止时等待正在发布的事务完成。

设计 MinIO 与 PG 的备份时间点需要可对应；恢复后先运行只读对账，再决定是否开放新入库。实际 RPO/RTO 需业务确定。

11 · 验收计划

场景验收标准
v2 对象能力回归目标 独立对象上传、筛选、下载、删除、桶级当前/日统计、失败重试与过期清理均可用，API 路径保持兼容。
上传凭证重放目标 客户端在凭证有效期内再次写 staging key，不改变已 ready 正式对象的内容或文档当前版本。
稳定 ID 与版本目标 同来源标识重复入库只保留一篇逻辑文档；有效新修订追加版本；旧版可读且附件清单不变。
文档类型目标 未知/停用类型不能新建；同一来源身份提交不同类型返回 409；按 doc_type 筛选正确；旧版本保留各自属性快照；重分类保留审计记录。
自定义标签目标 对象和文档均可选择已有标签或输入新名称；同租户并发创建同名标签只产生一个字典项；新标签随后可选；跨租户标签不可绑定。
按标签检索目标 对象/文档检索各自只返回直接绑定项；单标签及 all/any 多标签筛选、与类型/时间组合、游标翻页结果正确；不存在的标签返回空结果且不新建。
跨层删除保护目标 已引用对象的通用删除返回 409；发布引用与删除并发时恰有一个成功，永不产生 ready 版本引用 deleting/deleted 对象。
故障注入目标 对象上传、版本发布、当前指针更新前后中断均可重试或回收；对象和文档统计不重复。
规模装载目标 生成代表性的 3,000 万篇文档、对应对象以及实际比例的版本和附件关系；记录各表/索引/WAL/备份体积。
读性能目标 按 ID 获取当前版本 p95 ≤ 150 ms；版本列表 p95 ≤ 250 ms。目标值不含正文传输，需在指定硬件和并发下实测。
入库与恢复目标 按预计峰值持续入库 24 小时无丢失或重复版本；对象、文档两层统计正确；完成 PG 时间点恢复和 MinIO 对账演练。

待确认 峰值文档/秒、平均版本数、附件数、正文大小与并发读取量尚未给出，压测数据分布必须据此修订。

12 · 待决策项与选型边界

问题默认方案改变方案的条件
元数据主库建议 PostgreSQL团队已有成熟 MySQL 体系可继续用 MySQL；单机离线、主要只读可评估 SQLite；实测单主写入或跨地域要求超出能力时再评估分布式 SQL。
文档去重设计 按来源外部 ID 做逻辑去重；对象不自动按内容哈希去重。内容重复率高且物理成本显著时再引入去重与引用计数。
版本定义设计 每次有效抓取/解析产出版本。需明确“相同原文、不同解析器版本”是否产生新版本，以及来源 revision 的可信度。
文档类型清单设计 受控字典 + 稳定 code；类型在文档身份上，类型专有属性按版本快照保存。需提供实际文档类别、每类必填属性、允许附件角色，以及图片是否作为独立逻辑文档。
标签使用规则设计 租户内共享标签字典；对象与逻辑文档独立绑定；默认无继承。需按业务确定标签名称长度、每实体标签数上限、谁可新建/停用标签，以及是否需要按历史版本保留标签快照。
文件正文搜索设计 第一版不包含。若必须按词、段落或图像内容检索，另设抽取与搜索索引，不把文件内容塞进 PG 元数据表。
版本与删除策略设计 历史版默认保留；已引用对象的通用删除返回 409，无引用且超过保留期才回收。需确定保留期、删除权、法律冻结及成本预算。
