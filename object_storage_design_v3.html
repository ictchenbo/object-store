Solution Blueprint / 2026-10-09

文档、版本与附件管理服务
PostgreSQL + MinIO + FastAPI

设计 面向数千万篇文档及图片附件、持续多任务入库、按稳定文档 ID 读取和版本追溯。PostgreSQL 管理身份、版本、关系和查询；MinIO 保存正文与图片字节。

版本 v3核心对象：文档 / 版本 / Blob / 附件关系持续入库多租户可选HTML 单文件方案
核心选择

设计 以文档 ID 作为长期稳定身份；每次抓取或解析形成不可变版本。只有当该版本的正文和附件全部达到可读状态，才在同一 PostgreSQL 事务中更新文档的当前版本指针。Blob 保持不可变，引用关系由关系表表达。

主库

建议 PostgreSQL 作为正式共享元数据主库；单主高可用起步。总条数本身不要求分布式 SQL。

字节存储

设计 MinIO 保存正文、原始文件与图片；PG 只保存位置、哈希、大小、媒体类型和关系。

查询范围

设计 优先支持按 ID、来源标识、类型和时间读取；文件正文全文检索不在第一版内。

01 · 场景与范围

已知业务方向

  • 依据 用户补充：规模为数千万篇文档与图片，数据持续入库，按 ID 读取，需管理版本和附件关系。
  • 设计 支持多任务或多机器写入；按来源、类型、时间和有限差异化属性筛选。
  • 设计 正文可为 HTML、文本、PDF 等，附件与图片以 Blob 表示；解析出的文本可在后续接入检索引擎。

第一版边界

  • 设计 保留原始对象、处理后的正文及附件，但不在 PG 中保存大正文。
  • 设计 版本追加、当前版本切换、版本列表和附件列表可用；历史版本默认保留。
  • 设计 不承诺跨地域双活、OCR、内容全文检索或按图片内容搜索。
  • 待确认 是否需要法规留存、去重、删除权及文档级 ACL。
口径 文档数、版本数、Blob 数、附件关系数是不同指标。物理存储占用还包含 MinIO 冗余、对象版本和未完成上传，不可直接由 PG 逻辑字节推得。

03 · 领域与数据模型

documents稳定逻辑身份、当前版本指针
document_versions追加式历史，正文 Blob
document_assets版本与附件的关系
blobsMinIO key、哈希、大小、类型
表关键字段职责与约束
documentsid, tenant_id, source, external_id, doc_type, title, attrs_jsonb, current_version_id, created_at, updated_at设计 一篇逻辑文档一行。`(tenant_id, source, external_id)` 唯一；`current_version_id` 可空，且必须属于本 document。频繁查询字段用普通列。
document_versionsid, document_id, version_no, source_revision, ingest_key, raw_blob_id, body_blob_id, parser_version, status, captured_at, published_at设计 追加式版本。`(document_id, version_no)` 唯一；`(document_id, ingest_key)` 唯一以防任务重试重复建版。状态 staging / ready / failed。
blobsid, tenant_id, bucket, object_key, sha256, size_bytes, media_type, status, created_at设计 只保存对象存储定位信息。`(bucket, object_key)` 唯一；key 用服务生成的 UUID，正文和图片字节不入 PG。第一版不做自动跨文档去重。
document_assetsversion_id, blob_id, role, ordinal, reference_name, attrs_jsonb设计 版本与图片/附件的多对多关系；`(version_id, role, ordinal)` 唯一。引用名称保留原文中的链接或标识。
ingest_jobsid, tenant_id, source, external_id, ingest_key, status, attempts, next_run_at, last_error设计 独立记录处理过程和重试，不把高频任务状态堆在 documents 行上。
outbox_eventsid, aggregate_id, event_kind, payload, created_at, processed_at设计 同 PG 事务写入发布、统计、清理事件，供 Worker 幂等消费。
关系约束 当前版本属于对应文档这一条件必须由复合外键或等效数据库约束保证，避免指针误指其他文档的版本。删除 Blob 前必须确认所有正文、原文和附件引用均已解除。

设计 DOI、栏目、图像尺寸等差异化属性先按查询频率决定：常用条件提升为独立列；其余放 JSONB。版本和附件列表保持关系表，不不断追加进单个 JSON。

04 · 持续入库与版本发布

  1. 设计 采集器提交 source、external_id、ingest_key、文档类型和预期附件清单；API 用唯一约束定位或创建 documents，并创建 staging 版本。重复 ingest_key 返回原会话。
  2. 设计 API 为原文、正文和每个附件生成独立、不可覆盖的 Blob key 与短时上传凭证；采集器直传 MinIO。大文件的 multipart 编排作为独立实现项。
  3. 设计 采集器提交完成；服务对每个 Blob 执行 HEAD/stat，核验存在、大小和预期 SHA-256。若存储端不提供可信的该哈希核验，须采用受控流式校验或业务可信采集器证明，不能把 multipart ETag 当作 SHA-256。
  4. 设计 PG 单事务内：将 Blob 与版本置为 ready、写入附件关系、按发布策略更新 documents.current_version_id、插入 outbox_events。事务提交后新版本才对普通读取可见。
  5. 设计 发布策略默认“已完成的最高 version_no 成为当前版本”；晚到的旧来源修订保留为历史，不回退当前版本。若来源自身有可靠单调 revision，可按其排序。
一致性边界 MinIO 与 PostgreSQL 不共享事务。已上传但未发布的 Blob 属于暂存对象，必须由会话超时清理与周期对账回收；失败版本不会被当前版本指针引用。

05 · 按 ID 读取与附件访问

当前版本读取

设计 按 document ID 查 documents.current_version_id；一次读取版本和关联 Blob 信息。响应包括文档字段、版本号、正文对象描述和附件清单。正文可返回短时下载 URL 或由服务代理。

历史版本读取

设计 按 `(document_id, version_no)` 获取特定版本；版本列表按 version_no 倒序。附件关系固定在版本上，因此历史正文始终对应当时的图片与附件清单。

设计 默认 API 不在“文档列表”中批量展开全部附件；详情页按需获取，避免列表读造成大量 JOIN 或 N+1 请求。客户端只能访问已授权文档所引用的 Blob。

06 · FastAPI API 契约

设计 路径前缀 `/api/v1`；读写接口按 tenant_id 或业务访问范围授权。所有入库写操作要求 Idempotency-Key；错误体统一为 code、message、request_id。

07 · 索引与容量

表 / 查询首批索引选择理由
documents 按 IDPRIMARY KEY(id)；必要时 `(tenant_id, id)`设计 按 ID 定位是主路径；权限过滤必须包含租户或访问范围。
来源幂等UNIQUE(tenant_id, source, external_id)设计 同一来源对象只对应一个逻辑文档。
版本读取UNIQUE(document_id, version_no)；UNIQUE(document_id, ingest_key)设计 快速取历史版本，并约束重试。
附件列表(version_id, role, ordinal)设计 先按版本定位，再按角色和顺序展示。
文档筛选真实高频条件对应组合索引设计 来源、类型、时间组合需由查询日志和压测决定，不预建所有排列。
差异化属性按需添加 JSONB GIN 或表达式索引设计 避免把整个 JSONB 默认索引化导致入库成本上升。

判断 数千万篇文档本身不足以要求分布式数据库。documents 主要按 ID 读，默认不按时间分区；抓取历史、任务日志等按时间清理的数据可优先评估时间分区。分区键必须能被常见查询利用，否则可能增加维护和规划成本。PostgreSQL 分区文档

估算 若 3,000 万篇文档的有效字段平均为 1 KB，仅字段载荷约 30 GB（十进制）；不含行开销、索引、版本、附件关系、WAL、备份与预留空间。容量须由样本数据装载后实测。

08 · 一致性、幂等与对象回收

情形处理
重复采集相同文档设计 `(tenant_id, source, external_id)` 定位逻辑文档；同 ingest_key 返回同一版本，新的有效修订追加版本。
Blob 已上传，PG 发布失败设计 版本保持 staging；重试 complete；超过 TTL 的暂存 Blob 标记并清理。
附件上传不完整设计 整版不发布；详情仍读旧 current_version_id。允许重新上传缺失附件再完成。
两个任务并发发布设计 在文档行上串行更新当前版本指针，并比较版本顺序；唯一约束负责幂等。
删除某历史版本设计 先解除关系并确认不是当前版本；Blob 仅在无引用且保留期结束后删除。
PG 与 MinIO 不一致设计 定期比对 ready Blob 的对象存在性和暂存对象；缺失对象报警，不静默删目录。

设计 任务重试使用数据库持久化状态；统计与清理事件通过 outbox 事务写入。对账按 key 范围分页、限速、记录游标，并定期演练“PG 已恢复但 MinIO 对象缺失”及相反情形。

09 · 统计与观测

业务统计

设计 分别统计当前文档数、总版本数、正文 Blob 数、图片与附件关系数、逻辑字节。汇总表从发布/删除事件增量更新，并返回 as_of；每日抽样或分片校验明细。

运行指标

设计 监控入库速率、发布失败率、暂存年龄、Worker 积压、按 ID 查询 p95/p99、PG 索引与 WAL 增长、MinIO 容量及对象缺失数。

口径 “附件数量”默认指文档版本与 Blob 的关系数；同一图片被多个版本引用会计多条关系，但物理 Blob 数可能更少。应在报表中分别展示。

10 · 部署与恢复

组件生产建议恢复验证
FastAPI / Worker设计 至少双实例、无状态；连接池和并发上限受 PG 容量约束。重启和任务重试不创建重复版本。
PostgreSQL设计 单主与备库、PITR、独立备份；首先优化查询与索引，再考虑读副本。在隔离环境恢复到时间点，校验文档/版本/关系完整。
MinIO设计 分布式部署；生命周期与复制策略按保留要求设定。抽查由 PG blobs 定位的正文及附件均可读取。
脚本设计 实施阶段交付 compose.yaml、环境模板、Linux start.sh / stop.sh。启动前验证依赖、迁移与凭据，停止时等待正在发布的事务完成。

设计 MinIO 与 PG 的备份时间点需要可对应；恢复后先运行只读对账，再决定是否开放新入库。实际 RPO/RTO 需业务确定。

11 · 验收计划

场景验收标准
稳定 ID 与版本目标 同来源标识重复入库只保留一篇逻辑文档；有效新修订追加版本；旧版可读且附件清单不变。
故障注入目标 Blob 上传、版本发布、当前指针更新前后中断均可重试或回收；不出现指向未就绪 Blob 的当前版本。
规模装载目标 生成代表性的 3,000 万篇文档及实际比例的版本和附件关系；记录表/索引/WAL/备份体积。
读性能目标 按 ID 获取当前版本 p95 ≤ 150 ms；版本列表 p95 ≤ 250 ms。目标值不含正文传输，需在指定硬件和并发下实测。
入库与恢复目标 按预计峰值持续入库 24 小时无丢失或重复版本；完成 PG 时间点恢复和 MinIO 对账演练。

待确认 峰值文档/秒、平均版本数、附件数、正文大小与并发读取量尚未给出，压测数据分布必须据此修订。

12 · 待决策项与选型边界

问题默认方案改变方案的条件
元数据主库建议 PostgreSQL团队已有成熟 MySQL 体系可继续用 MySQL；单机离线、主要只读可评估 SQLite；实测单主写入或跨地域要求超出能力时再评估分布式 SQL。
文档去重设计 按来源外部 ID 做逻辑去重，Blob 不跨文档自动去重。内容重复率高且物理成本显著时再引入按哈希去重及引用计数。
版本定义设计 每次有效抓取/解析产出版本。需明确“相同原文、不同解析器版本”是否产生新版本，以及来源 revision 的可信度。
文件正文搜索设计 第一版不包含。若必须按词、段落或图像内容检索，另设抽取与搜索索引，不把文件内容塞进 PG 元数据表。
版本与删除策略设计 历史版默认保留，Blob 无引用且超过保留期才回收。需确定保留期、删除权、法律冻结及成本预算。
